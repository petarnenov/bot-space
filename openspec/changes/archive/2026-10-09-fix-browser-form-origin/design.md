# Design

## Context

Browser mutations pass through one identity middleware that authenticates the session, verifies same-origin context, parses the form, and compares a session-bound CSRF token. Human pages intentionally emit `Referrer-Policy: no-referrer`, so browsers that omit `Origin` provide neither of the two legacy origin signals.

## Goals / Non-Goals

**Goals:**

- Admit valid same-origin browser POSTs when referrer data is suppressed.
- Preserve explicit-origin precedence and mandatory CSRF verification.
- Make production failures diagnosable without returning secrets.

**Non-Goals:**

- Accept requests without browser-origin evidence and a CSRF token.
- Change OAuth, sessions, authorization, or endpoint behavior.
- Trust proxy forwarding headers as browser-origin evidence.

## Decisions

Use `Sec-Fetch-Site: same-origin` only as a fallback when both `Origin` and `Referer` are absent. Fetch Metadata is generated by the browser and distinguishes the valid no-referrer case from cross-site form posts. An explicit foreign origin remains authoritative so contradictory metadata cannot bypass protection.

Keep the session-bound CSRF comparison unchanged. Fetch Metadata supplements origin evidence and does not replace the per-session secret.

Return separate sanitized errors for origin rejection, malformed form data, and CSRF mismatch. This preserves confidentiality while identifying which protection rejected a valid production request.

## Risks / Trade-offs

- Older browsers may provide none of the three origin signals and remain rejected. This is fail-closed behavior; the mitigation is reloading in a modern browser rather than accepting unverifiable mutations.
- Client-supplied headers can be forged outside browsers. The mandatory authenticated SameSite session cookie and CSRF token remain the authorization boundary.
